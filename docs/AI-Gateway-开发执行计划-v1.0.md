## 1. 目的与边界

本计划不重复设计书中的接口、数据模型、配置值、失败语义和验收步骤。出现冲突时，以设计书 v1.5 为准；计划只做四件事：

1. 把设计书第 4 节的模块树拆成可交付的工作包。
2. 固定模块之间的依赖和接口冻结顺序，避免 Codex 多模块并行时互相返工。
3. 给每个工作包定义完成判据（DoD）和对应的 A 用例证据。
4. 排定波次、风险门禁和变更控制，保证 30～36 天总盘不被静默扩大。

不新增功能，不删除 A 用例，不改变默认配置、部署形态或验收口径。需要改变这些内容时，先修订设计书版本并同步模板，再更新本计划。

## 2. 基线与不变量

| 项 | 基线值 |
| --- | --- |
| 设计书 | v1.5，80 项配置、44 项验收用例、14 项功能映射、9 项性能目标 |
| 文档检查 | `python3 scripts/check_docs.py` 通过 v1.5/v1.4/v1.3/v1.2；`python3 scripts/test_check_docs.py` 11 组通过 |
| 框架 | FastAPI + SQLAlchemy 异步 ORM + asyncpg + PostgreSQL 16/17 + Alembic |
| 部署 | Ubuntu 24.04 LTS、x86_64/amd64、单实例、单 Uvicorn worker、离线依赖 |
| 并发基线 | 全局 16、课题默认 4、Key 默认 2；事件循环内准入，不用 Redis |
| 容量约束 | `DB_POOL_SIZE + DB_MAX_OVERFLOW >= 36`；鉴权、入口、HTTP 池满足 A44 |
| 阶段总盘 | P0 4 天；P1～P6 共 26 天；风险缓冲 6 天 |
| 验收 | A01–A44 全部通过；性能按 P0 冻结基线；真实上游兼容记录完整 |

任何一项基线变化都必须形成版本记录；Codex 不得在实现中直接修改设计约定的默认值、错误码、表结构或验收标准。

## 3. 计划分层与使用方式

| 层 | 内容 | 本文件的位置 |
| --- | --- | --- |
| L0 设计基线 | 需求、接口、数据模型、配置、A01–A44 | 引用设计书 v1.5，不重写 |
| L1 阶段计划 | P0–P6、M0–M6、30～36 天总盘 | 引用设计书 §13，本计划只排波次 |
| L2 模块执行计划 | M0–M10、工作包、依赖、DoD、A 用例映射 | 本文件主体 |
| L3 迭代看板 | 每周工作包状态、阻塞、证据位置 | 使用 §11 的字段，不进入设计书 |

使用方式：

- Codex 一次只领取一个工作包；PR 标题带工作包编号，例如 `WP-M4-02`。
- 每个工作包先确认输入的设计章节和接口，再写代码；接口未冻结的工作包不得先写。
- 完成判据以“测试 + A 用例证据 + 文档同步”三者为准，不以“代码写完”代替。
- 每周只更新工作包状态和证据位置，不反复改设计；设计变更走 §10。

## 8. 工作包完成判据（DoD）

一个工作包只有同时满足以下条件才能标记 Done：

1. 代码已合入，作用域仅限该工作包；没有顺手改其他模块的设计行为。
2. 单元测试通过；涉及数据库/网络的工作包有真实集成测试或可复现脚本。
3. 对应 A 用例有证据位置（测试 ID、request_id、SQL、日志或报告）。
4. 配置、迁移、接口文档与设计书一致；涉及文档时 `check_docs.py` 通过。
5. 不新增明文秘密；错误消息、日志、审计不泄漏凭证或正文。
6. 通过一次代码审查；PR 描述包含工作包编号、设计引用、A 用例、证据路径。
7. 计划看板状态、实际人日和阻塞项已更新。

不建议用“代码覆盖率”单独作为 DoD；本项目以 A 用例和真实故障证据为准。

## 10. 变更控制

- 设计行为变更：先升设计书版本（v1.6），同步模板，跑 `check_docs.py`/`test_check_docs.py`，再更新本计划；Codex 不得直接改设计约定。
- 计划变更：工作包拆分、顺序、估算变化记入本计划版本记录；超过总盘 20% 的偏差需重新评审。
- 范围变更：新增功能必须单独立项，不能用“顺手完善”名义进入首版。
- 证据变更：A 用例的通过标准、测试数据或配置偏差必须写进验收记录，不接受口头豁免。
- 版本标识：设计、模板、计划、代码提交使用同一基线标签，便于回溯。

## 11. 周报与看板

看板列：`待开始 / 进行中 / 待评审 / 阻塞 / 完成`。每个工作包记录：

- 编号、模块、负责人、计划人日、实际人日。
- 输入设计章节、输出/PR、依赖是否满足。
- 对应 A 用例、证据路径、未关闭问题。
- 阻塞原因、需要的决策、预计解除时间。

节奏建议：

- 周一：选定本周工作包，确认接口冻结和依赖。
- 周三：中期检查，只处理阻塞，不扩范围。
- 周五：更新证据和计划状态；未完成工作包说明原因，不带病进入下一波次。
- 每个波次结束做一次门禁评审，不以“已写了很多代码”代替退出条件。

## 12. 首次启动清单

1. 冻结 v1.5 基线：记录设计/模板版本和 commit；确认 11/11 文档测试通过。
2. 执行 P0-01～P0-06；产出环境基线、协议矩阵、代理信任链、配置冻结表和离线依赖预演。
3. 冻结 §4.1 的接口；未冻结不进入 W1 并行开发。
4. 按 W1 顺序启动 M0→M1→M2，先交付 M1 演示，再进入 W2。
5. 每个工作包按 §8 的 DoD 验收；每个波次按 §9 的门禁放行。
6. P0 结束后用实际速度校准 W1/W2 估算，更新本计划到 v1.0.1，不改变设计和 A 用例。
7. 进入 W4 前确认 A01–A44 证据目录、性能原始数据、离线恢复记录和签收资料齐全。

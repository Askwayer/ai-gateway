## 本地实测

执行 `scripts/p0_direct_echo.py`，使用锁定 Uvicorn 0.54.0 的真实 TCP 服务和 HTTPX 客户端，不是 ASGITransport。服务只绑定 127.0.0.1 随机端口，proxy_headers=False，单 worker；完成后停止服务，报告确认退出。

| 场景 | 结果 |
| --- | --- |
| 普通直连 | socket peer 与 client_ip 均为 127.0.0.1 |
| 伪造单个 XFF | 不改变来源 |
| 伪造多跳 XFF | 不改变来源 |
| 非法 XFF | 不改变来源 |
| Forwarded / X-Real-IP | 不改变来源 |
| 同一 peer 声称不同 IP | 仍识别为同一来源；不证明真实 NAT 设备行为 |
| IPv4-mapped IPv6 文本归一化 | 纯函数检查通过；不冒充 IPv6 TCP 实测 |
| 绑定 127.0.0.2 / 127.0.0.3 | 当前 macOS 均 ConnectError；没有增设系统地址别名，留待 Ubuntu 补验 |

原始报告：`.tools/p0-direct-echo-20261115.json`。六个直连 TCP 用例通过，多来源可行性失败独立记录，不能合并为“所有测试通过”。原型只实现空信任表直连行为，不作为正式入口中间件导入，不证明可信代理多跳解析能力。生产实现/完整 A41 仍归 P1/P2/P4。

复现命令（输出文件必须不存在）：

```bash
.tools/p0-candidate-venv/bin/python scripts/p0_direct_echo.py --output .tools/p0-direct-echo-NEW.json
```

## 直连部署约定

- TRUSTED_PROXY_CIDRS=[]；以原始 socket peer 为来源，忽略 XFF、Forwarded 和 X-Real-IP 对来源身份的影响。
- P1 生产启动器显式 proxy_headers=False、workers=1、reload=False。原型仅证明这个配置组合下本机来源行为，生产启动器仍需独立验证。
- 网关与内网上游不使用环境代理。用户参考文件里 OSS 的代理、其他应用的文件处理限制和 APP_ENV_FILE 行为不引入本项目；P1 应显式禁用 HTTPX 环境代理读取，部署时清理全局代理变量。
- 当前上游候选为 `http://172.31.34.204:5330/v1`。接口追加必须保留 `/v1`，例如模型列表候选为 `/v1/models`，不得重复追加或误删前缀。
- 客户端若经 NAT 汇聚，直连网关仍可能只看到同一 peer；同 IP 共享入口桶是设计行为，实际来源分布与速率是否需要调整由现场记录决定。

## A41 方法准备

| 轮次 | 方法和预期证据 | 执行阶段 |
| --- | --- | --- |
| 默认保护/伪造头 | 保持 default-protection、空信任表；记录 peer、client_ip、拒绝分类及恢复；同一 peer 的伪造 XFF 不生成新桶 | P4，依赖 P1/P2 正式入口 |
| 鉴权通道满 | 测试仓储在获得通道后进入可取消屏障，证明有界拒绝和释放；不添加生产调试开关 | P4 |
| 慢 DB | 在独立测试库执行参数化 pg_sleep；本轮预期睡眠期间超过 DB_OPERATION_TIMEOUT，原鉴权 SQL 不执行；保存 SQL/通道时间线 | P4 |
| 桶容量 | 优先 Ubuntu 验证实际可 bind 的 N+1 个回环源地址，N=INGRESS_IP_MAX_ENTRIES；每个来源应有实际 peer 证据 | 现场验证来源方法，P4 执行容量 |
| 回环不足时的备选 | 隔离实验代理，精确限定可信 peer，覆盖输入 XFF；声明为合成来源并记录配置偏差。此方案不改变生产直连拓扑 | 仅现场证明回环不可行后选定 |
| 速率/回收/恢复 | bucket-capacity 实验保持 N/TTL，调整速率满足设计的完成窗口；验证表满、TTL 回收、新来源进入，恢复默认配置后复测 | P4 |

本轮未实现生产令牌桶、未创建 4097 个地址、未运行 pg_sleep 注入；没有将 A41 标为通过。N+1 来源生成方式在目标 Ubuntu 的 bind/connect 证据到齐后才能最终冻结。

## A44 方法准备

保持 default-protection：同一来源 IP、额定并发，按设计的四课题/两 Key/每 Key 两请求分配。冷池允许启动 ready 已建立的连接，记录首次业务前 C0 与 connect/close/checkout 事件；不得 dispose 人造冷池。热池按设计预热到 min(G, pool_size)，保存同样事件。

每轮检查合法首请求无误拒绝、请求/usage/活动数可对账、最终名额与通道归零。实际 C0、等待时间、峰值连接、业务结果由 P4 实测；P0 只完成观测点和判定规则准备。所有写入和测试数据清理限 ai_gateway_test，测试夹具须核验实际库名及测试角色。

## 现场补验顺序

1. Ubuntu 主机预检：OS/架构、Python/glibc、CPU/内存、时钟、服务管理方式和停止时限。
2. 断公网安装候选依赖、执行导入检查；从目标网段连接 PG 和选定 Fast 上游。
3. 先执行公司 `/v1/models` 检查，再取得非流/SSE/usage/健康路径/探测参数及取消行为证据。当前开发机该检查 ConnectTimeout，仅说明当前访问路径未通。
4. 重跑直连回显，核对实际来源；预验证 A41 所需来源地址方案。实际生产入口与 A41/A44 的实现验收留到相应阶段。
5. 将结果填入配置冻结记录，复核连接额度与性能环境，完成 P0-04/P0-06 和 M0 签收。

本轮现场补验材料包含 `scripts/p0_preflight.py`、`scripts/p0_verify_dependencies.py`、`scripts/p0_direct_echo.py`、`scripts/p0_check_company_upstream.py` 及配置候选清单。旧离线依赖包没有后两份新脚本；传输时以本轮补验材料包为准，秘密 `.env.company` 必须另行受控配置，不随无秘密材料包分发。
